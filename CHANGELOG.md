# Changelog

## 4.1.3

- **Fixed: `dispose()` never released the leader lock.** Leadership was held with `await new Promise(() => {})`, on the reasoning that the lock dies with the tab — true, but a disposed instance is not a closed tab. The dead instance kept `<ns>-leader` for the life of the page, so the next instance on the same volume started as a **follower of a leader whose relay workers were already terminated**, and its first synchronous call waited for a reply that could never come until the 30s stall guard. The lock is now resolved on dispose, and a queued follower's bid is aborted so a disposed instance cannot be elected later. Covered by a test that stubs `navigator.locks` with the queueing semantics the real thing has, rather than mocking the election away.

### Known: a disposed instance still holds the volume open

- **Reopening the same volume after `dispose()` hangs.** A leader holds an exclusive `createSyncAccessHandle` on the volume's `.vfs.bin`, and nothing closes it on shutdown, so the next instance waits on a handle nobody returns. Measured in Chromium: sequential create/dispose cycles on one root fail from the second onward, while fresh roots run ~550 ms every time. Waiting does not help — a 500 ms or 3 s pause between cycles still fails, so the handle is not merely released late.
- Closing it in the relay's shutdown traded the hang for `EIO` on reopen, and flushing the engine first made it nondeterministic, so **that fix is not in this release**. One handle per volume is the intended design; the defect is that the count never returns to zero.
- Affects `dispose()` followed by reopening the *same* root in the same page — the documented "app that switches volumes" case. Unaffected: fresh roots, and keeping one instance for the page's lifetime.

### Demo

- The benchmark measured the demo's own redraw loop. `watch` fires per mutation and the page redrew on every one, so a benchmark making ~490 mutations had a follower tab issue ~490 full listings — each a round trip through the leader — *while it was being timed*. Redraws are coalesced and suspended during the benchmark. Follower writes, two real tabs in Chromium: create **98.5 → 9.6 ms**, overwrite **76.2 → 2.5 ms**, unlink **68.5 → 2.6 ms**.
- The main-thread panel builds its instance once instead of per click, which is what an app would do and sidesteps the volume-handle defect above. Five consecutive clicks run 74–262 ms; the second used to freeze the tab for 30s.
- Grid rebalanced — every panel but the file browser was stacked in the right column, which ran half again as tall as the left and pushed the benchmark and the log below the fold.

## 4.1.2

- **Fixed: `createServiceWorkerBridge` still resolved `swUrl` against the origin.** 4.0.1 fixed this in `filesystem.ts` and missed the second copy in `sw-bridge.ts`, so a **worker-hosted** instance on a subpath — the arrangement 4.1.1 moved the demo to, and the one Safari requires — registered a script that was not there. The failure surfaced two layers from its cause: a 404 on the service worker, then the instance could not become leader, then every call came back `EIO: i/o error, readdir '/'`. Both call sites resolve against `document.baseURI` now.
- The two paths are exercised separately: a page-hosted instance registers through `filesystem.ts`, a worker-hosted one through the bridge, so fixing one told nothing about the other. Verified under a subpath in Chromium *and* WebKit: no 404s, no `EIO`, leader elected, files listed.

## 4.1.1

- **Fixed: `swUrl` threw a `ReferenceError` in a worker.** 4.1.0 started resolving it against `document.baseURI`, which does not exist in a worker scope. A worker-hosted instance normally returns earlier via `swBridge` and never reaches that line, but one configured with `swUrl` and no bridge crashed instead of failing on a registration it could not perform anyway. It falls back to `location.href` off the main thread.

### The demo now runs the filesystem in a worker

Not a package change — `files: ["dist"]` — but it is the arrangement this library recommends for
Safari, and the reason is worth recording.

- **The Pages demo booted in ~30 seconds on Safari, about half the time.** Measured across repeated WebKit loads: `30207ms`, `30183ms`, ~`200ms`, ~`200ms`. The 30s is exactly `SPIN_STALL_TIMEOUT_MS`. `Atomics.wait` is illegal on a page's main thread, so a synchronous call busy-spins; on Chromium the relay progresses anyway, on WebKit the spinning page starves the worker's continuations and the reply never lands until the stall guard trips. Hosting the instance in a worker makes the wait a real `Atomics.wait` and the main thread stays free: **6 of 6 WebKit loads now boot in 240–374 ms.**
- **The readme framed this risk too narrowly.** It described main-thread sync stalls as an `opfs`-mode and follower-tab problem; it also hits a *leader* in the default `hybrid` mode on WebKit. Corrected.
- The demo gained a panel that runs sync calls on the page's main thread on demand and reports what actually happened — "works here" on Chrome and Firefox, an honest failure on Safari with the reason. Main-thread sync is not worker-only; Safari is the exception, and the demo now shows which is which instead of claiming either.

## 4.1.0

- **Added `fs.isLeader` and `fs.onLeaderChange(listener)`.** One tab per origin holds the lock and does the work; the rest relay their calls to it. That was documented architecture with no way to ask which one you are — and it is not cosmetic. A follower's synchronous calls cost a round trip to the leader, so **a benchmark taken in a follower is expected to be slower**, and one that does not say which role it ran in is not comparable. On Safari a follower's main-thread sync call cannot work at all, so knowing the role is how you decide to move the instance into a worker. Leadership moves when the leader goes away, so it is exposed as a live signal rather than a value you read once.
- The demo now names the role in a banner, labels its benchmark with it (`sync API · follower`), and explains that a follower measuring slower is expected. Close the leader tab and the badge flips without a reload.

A patch for one bug that only appears once the package is deployed somewhere other than a domain
root — which is to say, the case no local test server reproduces.

- **Fixed: a relative `swUrl` jumped to the site root.** It was resolved against `location.origin`, so an app served from a subpath — `/fs/` on GitHub *project* pages, `/app/` behind a proxy — asked the browser to register a script that was never there and got `A bad HTTP response code (404) was received when fetching the script`, followed by "Failed to connect to leader". ## 4.0.0

**The release that makes this library usable without installing it, and finishes `node:fs`.** Two headline
changes: it can now be loaded straight from a CDN with no build step, and the `node:fs` surface is
**complete — 134 of 134 functions, nothing excluded**. Nineteen real bugs were found and fixed along the way, eighteen of them by auditing every
method — and then every option, and then every function on its own — against a live `node:fs`.

**Upgrading:** the API you call is unchanged. Two small things can affect you — see Breaking.

### Breaking

- **`fsPromises.glob` returns an async iterator**, as node's does, instead of `Promise<string[]>`. If you were `await`ing it for an array, iterate it instead — or use the callback form, which still hands back the whole array:
  ```js
  for await (const path of fs.promises.glob('/src/**/*.ts')) { … }
  ```
- **`dist/index.js` grew from 327 KB to 460 KB** (+41%), the price of embedding the workers so CDN loading works. Paid by bundler users who never had the problem, to fix it for everyone else. Judged worth it: a library that cannot be tried without a build step mostly does not get tried.
- **`dist/workers/server.worker.js` is gone** — 103 KB of the old architecture, superseded by the sync relay. Nothing spawned it: not one `import` or `new Worker` anywhere in the source, tests or built output, and it was never reachable through `exports`. Listed here only because a file that used to ship no longer does.
- **An unhandled `'error'` event now throws**, as node's `EventEmitter` does, instead of being silently dropped. A stream error with no listener used to vanish and present as a hang with no diagnostic. It is emitted on a later tick, so `write()` still returns `false` rather than raising at the call site.

### Install it without installing it

- **Fixed: the package could not be loaded from a CDN at all.** Workers were located with `new URL('./workers/<name>.worker.js', import.meta.url)`, and `new Worker()` on a cross-origin URL is a `SecurityError` with no workaround available to the caller — so `import { VFSFileSystem } from 'https://esm.sh/@componentor/fs'` threw at construction. That is the lowest-friction way anyone tries a browser library, and it failed in a way that reads as "this library is broken" rather than "this package is mis-shipped". The worker bundles are embedded in the entry as source text and started as same-origin blobs ([worker-blob.ts](src/src/workers/worker-blob.ts)).
- **Fixed: Vite needed `optimizeDeps.exclude` to work.** Dependency pre-bundling rewrote those same `new URL(...)` calls and the workers stopped resolving, so every Vite user had to know one undocumented incantation before anything ran. There is no URL left to rewrite — verified against `vite dev` *and* `vite build` with a config containing nothing but the isolation headers.
- The **nested** worker needed the same treatment for a subtler reason: the sync relay starts the OPFS mirror worker, and now that the relay is itself a blob, `import.meta.url` inside it is a `blob:` URL that `./opfs-sync.worker.js` cannot resolve against. A nested worker has to carry its child's source, so the build runs in three stages — opfs-sync, then the relays with opfs-sync embedded, then the entries with the relays embedded ([build.mjs](src/scripts/build.mjs)).
- **The service worker is deliberately not embedded.** Its scope is derived from the URL it was registered from, so it has to stay a real file; multi-tab setups still point at `dist/workers/service.worker.js` (or `swUrl`). Unchanged.
- Pinned by [cross-origin-load.spec.ts](tests/benchmark/cross-origin-load.spec.ts), which serves `dist/` from a second origin and drives both the async **and the sync** path through it — the sync one matters, because only a running relay worker can answer it. A second test asserts the old URL form still throws `SecurityError`, so the first cannot quietly become vacuous.
- Corrected a readme claim that had been wrong for a long time: it said workers "are inlined at build time", and a code comment said the same. Neither was true until now.

### `node:fs` is complete: 134/134

Every function `node:fs` and `node:fs/promises` export now exists here, with **no omissions list**.
[api-surface.test.ts](src/tests/api-surface.test.ts) enumerates node's exports at runtime and
fails in *both* directions, so neither a missing method nor a stale "intentionally absent" entry
can survive a test run.

- **Added `fs.Utf8Stream`** — node 24's buffered append stream, the engine behind fast logging. Six methods and twelve getters, with the defaults, event order (`write` → `ready` → `drain`, then `finish` → `close`) and option validation read off a live `fs.Utf8Stream` rather than the docs. Batching is the point of the class, so `minLength`, `maxLength` (with its `drop` event), `append`, `mkdir`, `fsync`, `periodicFlush`, `contentMode` and `reopen` are real rather than accepted-and-ignored.
- **Added `fs._toUnixTimestamp`** — node's internal time coercion, under the same underscored name node uses.
- **Completed `FileHandle`'s EventEmitter surface.** 3.3.28 said it "is an EventEmitter now"; it forwarded five methods and none of the other ten. The missing ones — `removeAllListeners`, `listenerCount`, `listeners`, `prependListener`, `eventNames`, … — are exactly what long-lived objects reach for at teardown, so the gap was invisible to short-lived tests.
- **Added 15 missing `fs.constants`**, including the whole `UV_DIRENT_*` set that any code reading a `Dirent`'s type numerically depends on. The platform-only ones (`O_SYMLINK`, `UV_FS_O_FILEMAP`, `UV_FS_SYMLINK_*`) carry node's values so a bitmask read is never `undefined`, and are documented as having no behaviour behind them.
- **Exposed `fs.BigIntStats`**, so a `stat({ bigint: true })` result has a constructor to be tested against, like `Stats`/`Dirent`/`Dir`.
- Coverage against comparable libraries, measured the same way on the same denominator: **this 134/134 (100%)**, @zenfs/core 130/134 (97.0%), memfs 128/134 (95.5%).

### Six more bugs, found by checking every method against a live `node:fs`

Name parity was already asserted; [full-surface-parity.test.ts](src/tests/full-surface-parity.test.ts)
drove each function with a real call and its common error path against `node:fs` on a temp
directory, comparing return values, error `code`s and the resulting tree. Everything below was
green before this release.

- **`fsPromises.glob` returned the wrong type** — see Breaking. `for await (const p of fsp.glob(pattern))`, the form node's own documentation shows, iterated a promise and yielded **nothing**, silently. `await`ing it happened to work, which is exactly why it survived. An existing test asserted the old shape and was corrected rather than kept green.
- **`statfs` was missing `frsize`.** Node reports eight fields and this returned seven, so `statfs().frsize` was `undefined` and arithmetic on it produced `NaN`. Derived from `bsize` — equal on every modern filesystem — so no wire-format change and older workers keep working.
- **A negative time argument means "now", not a pre-epoch instant.** `fs.utimesSync(p, -1, -1)` stamps the current time in node; here it stamped one second *before* 1970. The rule is not in node's documentation — it surfaced from running `_toUnixTimestamp` against a live node across a table of inputs — and it reached every `utimes`, `futimes` and `lutimes` call.
- **`readFileSync(p, 'utf16le')` replaced unpaired surrogates with U+FFFD.** It decoded through `TextDecoder`, which follows the WHATWG substitution rule; `Buffer.toString('utf16le')` hands the code unit back untouched, so a file holding a lone surrogate could not round-trip. The fast native path is kept and only re-decoded when a U+FFFD actually appears.
- **`once()` was keyed by function rather than by registration.** `once('a', f)` plus `on('b', f)` — one handler on two events — meant firing `'b'` removed a listener meant to be permanent, and `once(e, f)` twice collapsed into one. Listeners are `{ fn, once }` records now, as node's are.
- **An unhandled `'error'` event was silently dropped** — see Breaking.

### `lchmod` and `lchown` were changing the wrong file

- **Fixed: `lchmod`/`lchmodSync`/`lchown`/`lchownSync` followed the symlink.** All four delegated straight to their following siblings, with a comment saying so — so `lchmodSync(link, 0o600)` changed the **target's** permissions, the one outcome the `l` prefix exists to rule out. Node leaves the target untouched. The engine already distinguished the two cases (it is how `stat` and `lstat` differ); the flag is carried in the request's existing flags word rather than as new opcodes, so a bundle built against an older worker ignores the bit and behaves exactly as it did before.
- Found by auditing the *coverage* rather than the code: five methods — `lchmodSync`, `lchownSync`, `fchown`, `lchmod` and `promises.lchmod` — had no differential test at all. They looked covered because their siblings were. [parity-coverage.test.ts](src/tests/parity-coverage.test.ts) now asserts that every one of the 134 exports is exercised against a live `node:fs`, so a method cannot again be implemented, typed, documented and never actually compared.

### Five more, found by testing every *option* rather than every method

Reachability is not depth: a method can be right in its default shape and wrong the moment an
option is passed, and options are where the semantics live
([option-matrix-parity.test.ts](src/tests/option-matrix-parity.test.ts)).

- **Fixed: `cp`'s `filter` was accepted and ignored.** It was not even declared on `CpOptions`, so every entry was copied whatever the callback returned — a filtered copy silently copied everything.
- **Fixed: `cp` turned symlinks into files when `dereference: true`.** The branch that recognises a link stat'd *through* it, so the link was never seen as a link. Node keeps links as links under `cp -r` either way; the branch decision is now always on the link itself.
- **Fixed: `glob` returned absolute paths for relative patterns.** Node reports matches **relative to `cwd`** unless the pattern is itself absolute, so `glob('*.txt', { cwd: '/src' })` should give `a.txt`, not `/src/a.txt` — joining the result onto `cwd` produced `/src//src/a.txt`. Existing tests asserted the absolute form and were corrected.
- **Fixed: `statfs`'s `bigint` option was ignored**, so `statfs(p, { bigint: true }).blocks` came back a `number` and mixing it with a real bigint threw `TypeError: Cannot mix BigInt and other types`.
- **Fixed: `lutimes` wrote the *target's* timestamps, not the link's** — the same defect as `lchmod`/`lchown`, in the fourth member of that family. All four now use the `NOFOLLOW` path.
- **Fixed: `mkdtemp` invented its parent directory.** `mkdtemp('/no/where/t-')` returned a path under a tree it had just created, where node answers `ENOENT` — so a typo'd prefix quietly produced a directory nobody would look in again.
- One divergence was confirmed as *ours being right*: node 24.18's `glob` calls its `exclude` callback erratically (five times for an absolute pattern, once for a relative one, never with `cwd`) and ignores what it returns. We honour the documented contract, and the test asserts our behaviour rather than chasing node's.

### Six more, found by giving every function its own differential test

[parity-coverage.test.ts](src/tests/parity-coverage.test.ts) is one test per function — 102 on
`node:fs`, 32 on `node:fs/promises` — with each case *written once and run twice*, against this
filesystem and against a live `node:fs` on a temp directory, comparing what came back and what it
did to the tree. Two sides that can never drift in what they were asked, because there is only
one copy of the ask. The table is checked against `Object.keys(nodefs)` in both directions, so
coverage is enforced rather than claimed.

- **Fixed: `fsync`/`fdatasync` reported success on a closed descriptor.** All four spellings (and `FileHandle.sync`/`datasync`) flushed the volume and returned, where node answers `EBADF` — so a use-after-close was silent at the one call whose entire purpose is to confirm the data is safe. The descriptor now travels with the request and the engine checks it; the volume-wide `flushSync()` sends none and is unaffected.
- **Fixed: a directory could be opened for writing.** `openSync(dir, 'w')` handed back a working descriptor instead of `EISDIR`. `O_TRUNC` *did* answer EISDIR internally, but the status was discarded — and for an implicit directory, one that exists only because it has children, `O_CREAT` created a file directly over it. Read-only opens still work, as in node, because `fstat` through the descriptor is the reason they exist.
- **Fixed: `watch` on a path that does not exist returned a watcher.** Node throws `ENOENT`; registering silently is worse than it sounds, because the caller's watch appears to be running and a mistyped path looks like a filesystem that never changes.
- **Fixed: the `FSWatcher` was not an `EventEmitter`.** `fs.watch(dir).on('change', …)` — the form node's documentation shows when the listener is not passed inline — died on `watcher.on is not a function`. It now emits `'change'` (eventType, filename) and `'close'`, with the listener argument registered for `'change'`, which is what node does with it too.
- **Fixed: `watchFile` returned `undefined`.** Node hands back a `StatWatcher`, so `fs.watchFile(p, cb).unref()` threw and the `'change'` event had nowhere to be subscribed. The watcher rides alongside the listener rather than wrapping it, so `unwatchFile(path, listener)` still finds the entry by the function the caller passed.
- **Fixed: `openAsBlob` on a file it cannot open reported the errno.** Node reports every such failure as `TypeError: Unable to open file as blob` with `code: 'ERR_INVALID_ARG_VALUE'` and no `path`, so code checking for `ENOENT` matched here and would not have in node. Not copied is *when*: node throws this synchronously out of a function that otherwise returns a promise, so `openAsBlob(missing).catch(…)` crashes rather than catching — this rejects, the same call made on `readFile(fd)`'s deferred error.

### External-change watching moved to where it can be switched off

- **The `FileSystemObserver` now lives in the scope that owns the instance**, not inside the mirror worker. Only the detected records cross into the worker, which still does the file I/O. The point is that `disconnect()` becomes a **synchronous** call on the unload path: an observer still attached when its scope is destroyed makes Chromium abort the **whole browser process** (`FATAL: Detected dangling raw_ptr`, a use-after-free in Chromium's own C++), and an observer inside a nested worker could never be detached in time — a page can post a shutdown at `pagehide` but cannot wait for it.
- **A worker-hosted instance no longer watches for external changes.** There is nowhere safe to put the observer: the page kills the worker outright. Hosting it on the page on the worker's behalf was tried and measured *worse* — one more observer that nothing reliably detaches, since `pagehide` does not fire when a page is closed programmatically. Mirroring outward is unaffected in every mode.
- **Added `disposeAll()`**, alongside the per-instance `fs.dispose()`. Its registry is shared across module copies via `globalThis`, because a page can legitimately load the library from two URLs (a bundle and a CDN) while the resources at stake — OPFS handles and observers — are per-origin. Worth calling from anything that owns the page lifecycle.
- **Honest note on the crash:** this reduces it, it does not eliminate it. The browser suite still trips it about once per full run and keeps one retry. The only configuration measured as fully deterministic (three consecutive runs, retries off, zero crashes) was registering no observer at all, which is too high a price for a feature that works. It is a Chromium bug, not something this code can be careful enough to avoid.

### `stat` on a directory is 3.3× faster

- Computing a directory's `nlink` (`2 + subdirectories`) went through the helper `readdir` uses: it allocated an object and a string per child, built an array, and then **sorted** it — to produce one integer. Sorting cannot change a count. A counting-only path allocates nothing per child beyond the lookup key: **37.6k → 122.8k stats/s**, closing the gap with `stat` on a file from 42× to 13.6×, and the mixed list-and-stat workload is **1.33× faster** end to end.
- The invariant is pinned directly rather than against the host, because directory `nlink` is filesystem-specific: the POSIX rule is `2 + subdirectories`, which ext4 and this VFS follow, while APFS answers 4 where ext4 answers 3.

The alias re-exports this package and pins it exactly, so the two are always the same code at the same version.
- **Four runnable examples** in [examples/](examples/), each loaded in a real browser by a test so a broken one fails the suite rather than the reader.
- **`npm run release`** publishes both packages in the one order that works, after a preflight that refuses to start on a version mismatch, a missing changelog entry, or an already-published version. See [RELEASING.md](RELEASING.md), which also explains why every version gets published.

## 3.3.29

Five divergences in the stream layer added by 3.3.28, found reviewing it rather than by a failing test — the suite was green through all of them. Each is now pinned against a live `node:fs` in [stream-parity-fixes.test.ts](src/tests/stream-parity-fixes.test.ts).

- **Fixed: `createReadStream(p, 'utf8')` corrupted every multi-byte character that landed on a 64 KB chunk boundary.** Each chunk was decoded with its own `TextDecoder`, so a character split across two chunks became two invalid fragments and decoded to two U+FFFDs — silently, since the text either side was fine. A 65546-byte file returned `é` from node and `�` from us. This was a **regression 3.3.28 introduced**: the faulty decoder is older, but `createReadStream` previously computed the `encoding` option and never applied it, so the bug was unreachable until the option was correctly wired up. Encoding is now carried across chunks by a resumable decoder ([`createStringDecoder`](src/src/encoding.ts)), node's `string_decoder` in miniature — including holding back a trailing UTF-16 lead surrogate so an astral character split between chunks is not emitted as two lone surrogates, and flushing a truncated sequence at EOF rather than dropping it.
- **Fixed: a stream built from a `FileHandle` ignored the handle's position**, reading from byte zero and never advancing the cursor. After `handle.read(buf, 0, 2)` on `'ABCDEFGHIJ'`, node's `handle.createReadStream()` yields `'CDEFGHIJ'`; ours yielded the whole file. The same mistake 3.3.26 fixed in `FileHandle.readFile()`, reintroduced in new code that had no reason to know about it. Applies to `createWriteStream` and `readableWebStream` too, and a caller-supplied `fd` passed to `fs.createReadStream` now behaves the same way, as node's does.
- Fixing that surfaced a second thing the docs get wrong: **`end` is a byte budget, not an offset.** A handle at position 2 given `{ end: 3 }` yields *four* bytes in node, not two; with `start` present it is absolute and inclusive again. Read off a live `node:fs`, and identical to the old arithmetic for a path-backed stream, whose cursor is always zero.
- **Fixed: leaving a `for await` loop early leaked the file handle.** `break`, `return` or a throw in the loop body left the stream paused and the handle open forever; node destroys the stream and closes it. Worse here than in node — in the browser these are OPFS sync access handles holding an **exclusive** lock, so one leaked handle blocks every later open of that file for the life of the page.
- **Fixed: `write()` after `end()` was a race rather than an error.** `_finished` was only set once the queued writes had drained, so a late write was accepted and queued; whether it reached the file, hit `EBADF`, or wrote through a closed handle depended on which won. Node reports `ERR_STREAM_WRITE_AFTER_END` the moment `end()` has been seen, and now so do we — which also freezes the write chain, closing the window where a write could be appended after `end()` had already captured it.
- **Fixed: `ws.write(str, 'latin1')` ignored the encoding** and always wrote UTF-8 — `'é'` went out as `[195,169]` where node writes `[233]`. Per-write encodings and the stream-level `encoding` option are both honoured now, through the same `encodeString` the rest of the library uses.
- Also measured: the fixes remove an allocation per chunk (`TextDecoder`) and per write (`TextEncoder`) rather than adding any. `Stats` construction is unchanged at 5.5× the old literal.
- **Fixed: every filesystem instance leaked a worker and a `FileSystemObserver`, with no way to release them.** The OPFS mirror worker was spawned into a local variable the sync relay immediately dropped, so nothing could terminate it; inside it, a **recursive** `FileSystemObserver` was registered on the origin's storage and never disconnected. `setMode()` terminated the two relay workers and orphaned the mirror worker along with its observer. There was no public teardown at all — so a page that opened several volumes, or switched modes, accumulated live observers on OPFS for as long as it stayed open. Added `fs.dispose()` (and `Symbol.asyncDispose`, so `await using` works); `setMode()` now shuts the relay down properly first, and an instance also tears its workers down on `pagehide` — skipping the back/forward cache case, where the page may be restored. Named `dispose` because `close(fd)` is already node's descriptor API.
- 1563 Node tests pass across 83 files, plus 36 browser tests in Chromium.
- **Not a library bug, recorded so it is not re-investigated:** Playwright's `chrome-headless-shell` aborts the browser process with `FATAL: Detected dangling raw_ptr in unretained` after the heaviest browser specs, which takes the next test with it. That is a use-after-free in Chromium's own C++ — JavaScript cannot create one — and the leak fix above does not stop it, nor does deliberately leaking an observer reproduce it. Release Chrome ships the detector off. The Playwright config now retries once, with the reasoning written down there.
- **Not fixed, and worth stating:** `readFileSync(p, 'utf16le')` replaces a lone surrogate with U+FFFD where node preserves it, because `decodeBuffer` goes through `TextDecoder`, which follows the WHATWG rule. Pre-existing, unrelated to streams, and not something the stream work touched.

## 3.3.28

- **Added the whole of `FileHandle`'s stream surface**, none of which existed: `createReadStream`, `createWriteStream`, `readLines` and `readableWebStream`. `FileHandle` is also an EventEmitter now and emits `'close'`, as node's does.
- **Fixed: read streams were not async iterable.** `for await (const chunk of fs.createReadStream(p))` — the ordinary way to consume a readable in node — threw *"stream is not async iterable"*, because `NodeReadable` had no `Symbol.asyncIterator`. It pauses between chunks, so a slow consumer applies backpressure rather than buffering the whole file. This was found only because `readLines` is built on it.
- Ownership matches node, verified against a live `node:fs`: a stream built from a handle **closes that handle** when it finishes, so `handle.stat()` afterwards is `EBADF`; `autoClose: false` opts out. A caller-supplied `fd` passed to `fs.createReadStream` stays the caller's to close — a different default, and both are pinned by tests.
- `fs.createReadStream`/`createWriteStream` and the new handle methods now share **one** implementation ([handle-streams.ts](src/src/handle-streams.ts)). Two independent copies of stream plumbing is precisely the shape that produced the wire-format bugs of 3.3.7 and 3.3.21.
- `readLines` follows `readline`: a trailing newline yields no final empty line, CRLF is stripped, and a line spanning several chunks is reassembled.
- **Fixed: the README documented the Streams API incorrectly** — it described `createWriteStream` as returning a WHATWG `WritableStream` with `getWriter()`, which it never did, and showed a `for await` loop over a read stream that could not work until this release.

## 3.3.27

- **`Stats`, `BigIntStats`, `Dirent` and `Dir` are real classes now**, exported from the package and reachable as `fs.Stats`/`fs.Dirent`/`fs.Dir`. They were object literals, so `stats instanceof fs.Stats` — how a good deal of node code type-tests these — was not merely false but impossible; there was nothing to be an instance of.
- **Building a `Stats` is 5.4× faster.** The literal allocated eleven objects per `stat`: seven closures for `isFile()`/`isDirectory()`/… and four `Date`s for `atime`/`mtime`/`ctime`/`birthtime`, eagerly, whether or not the caller read them. The predicates now live on the prototype and read `mode & S_IFMT` exactly as node's `Stats._checkModeProperty` does, and the dates are lazy getters. Even the worst case — a caller that does want a `Date` — is 2.4× faster ([stats-alloc.bench.ts](src/tests/stats-alloc.bench.ts)).
- **`Object.keys(stats)` and `JSON.stringify(stats)` now match node**, field for field and in node's order. They did not before: the four `Date`s were own properties where node builds them lazily, and `Dirent` carried `path` as a third own property, so serialising an entry emitted a field node does not.
- **Fixed: `fs.constants` did not exist on the instance.** Only `fs.promises.constants` did — despite a comment claiming they were the same — so `fs.access(p, fs.constants.F_OK)`, the canonical form, read a property of `undefined`.
- **`Dir` gained `readSync()` and `closeSync()`**, half of node's `Dir` API and previously absent, plus `ERR_DIR_CLOSED` on use-after-close and handle release when iteration ends early. `opendir` was two separate object literals — one per open path — that could and did drift apart; both now build the same class. **`opendir`'s `recursive` option was accepted and ignored**, silently returning only the top level; it works, in the sync and async forms.
- **Fixed: `glob({ withFileTypes: true })` entries were missing `path`**, so a glob result was shaped differently from a readdir result. One `Dirent` definition now serves `readdir`, `glob` and the recursive walk.
- Recursive `readdir` copied `isFile`/`isDirectory`/… *by reference* off each source entry, which only worked while they were per-instance closures — with the predicates on a prototype a bare reference lands on an object with no type and answers false for everything. Entries are re-parented through a proper clone instead.
- Measured and kept anyway: the `Dirent` class is a few nanoseconds **slower** to construct than the literal it replaced, since the private type slot costs more than the seven closures saved. It is there for `instanceof`, for node's own-property shape, and so the three producers cannot disagree. Recorded in the benchmark so the trade-off stays visible. A first attempt used a symbol-keyed slot instead, which pushed the object into dictionary mode and measured worse still — real `readdir` throughput went up 9% on the switch to a native private field.
- Two deliberate divergences, both for backward compatibility: `Dirent.path` survives as a getter (node deprecated it and **removed** it in v24), and `Stats.atimeNs`/`mtimeNs`/`ctimeNs`/`birthtimeNs` stay readable as getters (node has them on bigint stats only). Neither shows up in `Object.keys` or `JSON.stringify`.
- 1521 Node tests pass across 81 files, plus 80 browser tests across Chromium, Firefox and WebKit.

## 3.3.26

- **Added: a file descriptor may be used in place of a path** in `readFile`, `writeFile` and `appendFile` — long-standing Node behaviour that was simply missing, and the last gap the 3.3.25 sweep left open. The semantics are not the path semantics, and all of them were taken from a live `node:fs` run rather than the docs: the operation starts at the descriptor's **current position** and advances it, `writeFile(fd, …)` does **not** truncate, the descriptor is left **open**, and `flag`/`mode` are ignored. The raw-number form is on the sync and callback APIs; `fsPromises` takes a `FileHandle` instead, which is now accepted in the path position of `readFile`/`writeFile`/`appendFile`.
- **Fixed: `FileHandle.readFile()` always read from byte zero** instead of the cursor. `open` leaves the cursor at 0, so it looked right until the handle had been read from — after `read(buf, 0, 3)` node returns the file from byte 3 and a second `readFile()` returns `''`, where we replayed the whole file both times and never moved the cursor. `handle.writeFile()` had the same hardcoded position.
- **Fixed: `FileHandle.appendFile()` sought to end-of-file.** In Node it is a documented **alias of `writeFile`** — the appending comes from O_APPEND on the flag, not from the method — so on an `'r+'` handle `appendFile('B')` over `'AAA'` gives `'BAA'`, not `'AAAB'`. It also stopped issuing the `fstat` it used to need to find the end: **1.42× faster** in the in-memory harness ([async-overhead.bench.ts](src/tests/async-overhead.bench.ts)), and worth more in a browser where each round trip crosses a worker boundary. Three tests asserted the old wire sequence and were rewritten; `handle.writeFile`/`appendFile` also honour a string encoding now, which they silently ignored.
- **Fixed: 23 of 30 `fs.promises` methods threw synchronously where Node rejects.** The class methods were not `async`, so `toPathString` ran before any promise existed and the exception escaped past `.catch()` — surfacing in a browser as an uncaught error rather than a handled rejection. Node's three APIs deliberately disagree about this (`fs.statSync({})` throws, `fs.stat({}, cb)` throws *at the call site*, `fsPromises.stat({})` rejects) and all three shapes are now reproduced, with the callback layer validating paths itself so it keeps throwing. Costs one microtask per promise call — about **19 ns**, ~1% of the cheapest possible call in the fastest transport, and far less against a real browser round trip.
- **Fixed: `toPathString` threw a bare `TypeError` with no `code`.** It now carries `ERR_INVALID_ARG_TYPE` with Node's message shape, so callers can branch on `err.code`. `realpath` is Node's one exception to path validation — it stringifies its argument, so `realpathSync({ toString: () => '/tmp' })` resolves and a non-path gives `ENOENT` — and that looseness is now reproduced rather than rejected, since being stricter than Node breaks working code.
- **Fixed: reading a descriptor opened on a directory returned an empty buffer** instead of `EISDIR`, making a directory indistinguishable from an empty file. `lchmod`, `lchown`, `lutimes`, `statfs` and `mkdtemp` now accept `Uint8Array`/`URL` paths and validate them, where they previously took only strings and coerced anything else into a path — `mkdtemp(123)` used to *succeed*.
- One deliberate divergence added, documented in the README: `fs.readFile(-1, cb)` reports the bad descriptor **to the callback**. Node defers the check and then throws it uncaught from a later tick, taking the process down; that is not worth reproducing.
- 1497 Node tests pass across 80 files, plus 80 browser tests across Chromium, Firefox and WebKit.

- **Fixed: an unrecognised flag string silently opened read-only.** `fs.openSync(p, 'zz')` returned a working descriptor that could not do what was asked; Node raises `ERR_INVALID_ARG_VALUE`, and now so do we.

## 3.3.24

- **Fixed: `utimes` read its time arguments as milliseconds where Node reads seconds — a silent 1000× error.** `fs.utimesSync(p, 1600000000)` means September 2020 in Node and stamped January 1970 here. `toEpochMs` now follows Node's `toUnixTimestamp`: a bare number or a numeric string is **seconds**, a `Date` is used as-is, and `NaN`/`Infinity`/unparseable values raise `ERR_INVALID_ARG_TYPE` instead of writing `NaN` into the payload. Applies to `utimes`, `futimes` and `lutimes`.

## 3.3.23

- **Established the cost floor, and found that the bottleneck is a different thing in each browser.** [opfs-floor.spec.ts](tests/benchmark/opfs-floor.spec.ts) measures a bare `FileSystemSyncAccessHandle` with no VFS involved, so per-operation numbers can be read against what the platform itself charges. A raw write costs **0.22 ms on Chromium, 0.12 ms on Firefox and 0.004 ms on WebKit** — a 50× spread — and on all three it is flat in size: 64 bytes costs the same as 8 KB.
- **This corrects the conclusion in 3.3.22.** "We are at the storage floor, so there is nothing to optimise" is true *on Chromium* and wrong elsewhere. Chromium is storage-bound: five writes per create at 0.22 ms each accounts for the whole measured cost, so no code change helps. WebKit is the reverse — storage is nearly free there, it creates files **~10× faster than Chromium** (12433/s vs 1209/s), and its slowest operations are `stat` and `exists`, which never touch storage at all and are 3–5× slower than Chromium's because they are pure SharedArrayBuffer round-trips. On Safari, per-operation overhead is what matters and write volume barely does.
- It also explains a pattern from earlier releases: optimisations measured against an in-memory handle (the allocator in 3.3.13, `readdir` in 3.3.7) looked much larger than they did in Chromium. Chromium's storage cost hides CPU savings; WebKit's does not. The readme now says to measure in the engine you care about.
- **Deferred metadata commits are ruled out, with evidence.** 3.3.22 identified batching the bitmap and superblock writes as the one remaining lever, worth perhaps 40% on Chromium, and flagged it as a durability decision. Testing it settles the question: rolling the superblock back to simulate a crash mid-batch does not leave a stale-but-usable volume, it leaves an **unmountable** one — `Corrupt VFS: inode 21 path out of bounds` — because inodes then reference path-table offsets past the recorded `PATH_USED`. That failure mode is not acceptable behind an opt-in flag either, so the idea is closed rather than parked.
- Readme's cost section rewritten with the three-engine table and what follows from it. No behaviour changed; 1324 Node tests pass, plus the browser suites.

## 3.3.22

- **Profiled the hot path against real OPFS and published the cost model.** No optimisation landed this release — the measurement says there is nothing left to take without trading durability, and that is worth stating plainly rather than shipping a change that looks like a win. [profile-hotpath.spec.ts](tests/benchmark/profile-hotpath.spec.ts) is checked in so the numbers can be re-taken.
- **The finding: cost tracks the number of OPFS writes an operation makes, not the bytes it moves.** Creating a 256 B file costs the same as creating an 8 KB one (1209/s vs 1189/s in `vfs` mode), because each `handle.write` carries a large fixed cost. Instrumenting the handle shows a create needs **five** — path-table entry, file data, inode, free-block bitmap, superblock — each landing in a different region of the volume, so no two can be combined. An overwrite that fits its existing blocks needs **two**, and measures ~2.5× faster, matching the write-count ratio almost exactly. Metadata reads never touch storage at all: `stat` runs at 87k/s, `exists` at 121k/s.
- **Why nothing was cut:** the two removable writes are the free-block bitmap and the superblock, and both exist to keep the volume mountable after a crash. Deferring them across a burst would cut a create from five writes to three, but it widens the window in which a killed tab leaves the superblock describing a volume that no longer matches its inode table. That is a durability decision, not a performance tweak, and not one to make silently.
- **Corrected an imprecise claim in the readme.** The mirror was described as never adding latency. True for an individual call — the response is written before mirroring is queued — but it costs *sustained throughput*, because the mirroring runs on the same relay worker the next request needs: creates measure ~1200/s in `vfs` mode against ~750/s in `hybrid`. The readme now says which of the two it is, with the measured table.
- Added a "What operations cost, and why" section with the full measured table for both modes and the practical consequences: prefer overwriting to creating, batch small files rather than shrinking writes, and expect `stat`/`exists`/`readdir` to be unaffected by the mirror.
- 1324 Node tests pass, plus 23 browser tests across Chromium, Firefox and WebKit.

## 3.3.21

- **Fixed: `createWriteStream` lost data when writes were queued in the same tick.** `ws.write('abc'); ws.write('def')` produced **`'def'`** — the first write was gone. `NodeWritable.write` dispatched each chunk without awaiting or queueing the previous one, so both writes read the stream's file offset before either had advanced it, started at the same position, and the second overwrote the first. Writing several chunks in one tick is the ordinary way to use a write stream, so this is silent data loss on a headline feature.
- **And a second race one step later:** `end()` called its finish path immediately, closing the file handle while queued writes were still in flight. Both are fixed by serialising the stream's work through a promise chain — each write starts where the previous finished, and `end()` drains the queue before closing. A failed write settles the chain instead of rejecting it, so one error cannot strand every later write or leave `end()` waiting on a promise nobody resolves.
- **New differential fuzzer for the stream layer** ([fuzz-stream-parity.test.ts](src/tests/fuzz-stream-parity.test.ts)). Read streams are fuzzed across their windowing options (`start`, `end`, `highWaterMark`, including `end` past EOF), where an off-by-one silently truncates. Write streams are fuzzed over random chunk sequences with varying sizes — deliberately varied, so a mis-ordered write cannot be masked by a later one covering it. Both compare bytes against real `node:fs`.
- Verified through the **real relay and OPFS** too, not only in Node: [instance-parity.spec.ts](tests/benchmark/instance-parity.spec.ts) now checks that synchronously-queued writes land in order in Chromium, Firefox and WebKit.
- Honest note on how this was found: not by the fuzzer, but by the throwaway check that streams ran in the Node harness *before* writing it. The four-line probe printed `'def'`. The fuzzer exists now so the guarantee is permanent.
- 1323 Node tests pass, plus 18 browser tests across all three engines.

## 3.3.20

- **New differential fuzzer for the promise API** ([fuzz-async-parity.test.ts](src/tests/fuzz-async-parity.test.ts)). The async path is not the sync path with `await` in front: it hands `(op, path, data, fdArgs)` to a relay that re-shapes the request there, and that second shaping step is exactly where a wire-format bug once lived — `FTRUNCATE` was encoded with a uint32 length on the async side and a float64 everywhere else, so `await fileHandle.truncate(n)` was rejected outright (3.3.7). 200 operations per seed, including `FileHandle` truncate/write/readFile, with every outcome and the whole final tree compared.

That is not a detail: if removing a cyclic link reported `ELOOP`, a cycle would be impossible to clean up. All seven behaviours are pinned against real `node:fs` in [node-parity.test.ts](src/tests/node-parity.test.ts).

## 3.3.19

- **Fixed: file-descriptor access modes were not enforced at all.** The low two bits of an fd's open flags are its access mode (`O_RDONLY`/`O_WRONLY`/`O_RDWR`), and nothing checked them. Reading through a descriptor opened `'w'` or `'a'` returned **0 bytes instead of `EBADF`**, and writing through one opened `'r'` **succeeded**. Code that opens a file read-only as a safety measure got no error when something wrote to it, and code that treats a 0-byte read as end-of-file saw a silent empty file rather than the error Node raises. All three operations now match `node:fs`, verified per flag across `r`, `r+`, `w`, `w+`, `a`, `a+`: read and write report `EBADF`, while `ftruncate` on a read-only descriptor reports **`EINVAL`** — a different code, because truncating through a read-only fd is a bad argument rather than a bad descriptor.
- **New differential fuzzer for the fd API** ([fuzz-fd-parity.test.ts](src/tests/fuzz-fd-parity.test.ts)), which found the above. The existing fuzzer covers path operations, which are stateless; an fd carries a position and flags that every operation mutates, so a bug can need a particular interleaving to appear. Each step opens, reads, writes, truncates, stats or closes through both filesystems with identical arguments, compares the result *and the bytes actually delivered*, and re-compares each file's whole contents between steps so a divergence is caught at the operation that caused it.
- One existing engine test was asserting the bug: it opened with `O_CREAT|O_TRUNC` and no access-mode bits — which is `O_RDONLY` — and then wrote through the descriptor. Confirmed against `node:fs` that this must fail with `EBADF`, and corrected the test to pass `O_RDWR` as it evidently intended.
- **Excluded from the fd fuzzer, with reason:** an explicit write position on an append-mode descriptor. Whether `O_APPEND` overrides an explicit offset is genuinely platform-split — POSIX and macOS honour the position, Linux appends regardless, a deviation documented in its own `man pwrite`. We follow Linux, so comparing against macOS Node there would test the host platform rather than this library.
- 1302 Node tests pass, plus 24 browser tests across Chromium, Firefox and WebKit.

## 3.3.18

- **`readdir({ withFileTypes: true })` is 1.86× faster** — 2159 → 4010 listings/sec for a 500-entry directory, measured against **real OPFS** in Chromium with the change reverted and re-applied. It was still on the old shape after 3.3.7 optimised the names-only path: a full path built per child by concatenation, the long strings sorted, then the name sliced back out, and one intermediate `Uint8Array` per entry. It now sorts the child index's names directly and writes UTF-8 into the response buffer with `encodeInto`, building a full path only for the one lookup that genuinely needs it — classifying each child as a real inode or an implicit directory. Unlike the allocator change in 3.3.13, this one *does* show against real storage: it is per-entry CPU work multiplied by 500.
- **Withdrawn: the two `cp -r` "divergences" recorded in 3.3.16 are not ours to fix.** Characterising them against real `node:fs` (v24) showed **Node aborts the process** on two of these combinations — copying onto an existing dangling link (`equivalent: Operation not supported`) and copying a tree containing a cyclic link (`weakly_canonical: Too many levels of symbolic links`). Both are uncaught C++ exceptions, not throwable errors; there is no `catch` that helps. Matching that in a browser would mean killing the tab, which is strictly worse than what we do. Our behaviour — copy links as links, always terminate — is kept deliberately and pinned by [cp-symlink-edges.test.ts](src/tests/cp-symlink-edges.test.ts), which records the Node output as evidence rather than asserting a parity we have declined.

## 3.3.16

- **New differential fuzzer against `node:fs`** ([fuzz-parity.test.ts](src/tests/fuzz-parity.test.ts)). It runs a random sequence of operations against both filesystems with identical arguments, compares the outcome of *every* operation, then compares the entire resulting tree — path, type, size, contents and permission bits. Seeds are fixed so a failure reproduces exactly. It found four real divergences on its first run, three of which are fixed below; the hand-written suites had missed all four because each needs a specific *order* of operations to appear.
- **Fixed: `cp` into its own subtree never terminated.** `cpSync('/x', '/x/z', { recursive: true })` recreated the destination inside itself on every pass — an unbounded loop that hung the test runner for four minutes when the fuzzer generated it, and in a browser means a frozen tab and a filling disk. Node rejects both this and `src === dest` with `ERR_FS_CP_EINVAL` before copying anything; so do we now, in the sync, callback and promise paths. The drives layer guarded exactly this in 3.3.0 — `VFSFileSystem.cp` never was. The guard runs once per public entry point, not inside the recursion, whose destinations are legitimately inside the destination tree, and a sibling that merely shares a name prefix (`/xy` vs `/x`) is still copyable. [cp-self-copy.test.ts](src/tests/cp-self-copy.test.ts)
- **Fixed: symlink cycles reported `ENOENT` instead of `ELOOP`.** Path resolution returned "not found" for both a missing path and a chain that went in circles — the depth checks even carried `// ELOOP` comments, but the information was thrown away at every call site, so a caller could not tell a broken link from an absent file. The resolvers now record *why* they gave up, and `stat`, `read`, `truncate` and `chmod` report it. Care was needed in `stat`, which calls `isImplicitDirectory` between the failed resolve and the return — that resolves too, and would have reset the flag; the reason is captured first. A plain missing path still reports `ENOENT`.
- **Fixed: `copyFile` did not preserve the source's permissions.** The destination is created through the write path, which applies the default file mode, so copying a 0600 file produced a 0644 copy. `copyFile(2)` and Node both give the copy the source's mode. Fixed for both the block-copy and empty-file paths, and so for `cp -r`, which is built on it. The fuzzer found this as a single differing entry in a 7-entry final tree — exactly the kind of quiet divergence a whole-tree comparison exists to catch.
- **Found and documented, not fixed:** writes through a **dangling** symlink overwrite the link where Node follows it and creates the target (the fix is in `engine.write`, the hottest path in the library, and was not worth rushing at the end of a session); and two `cp -r` edge cases — `ELOOP` over a symlink cycle, and `EEXIST` overwriting a destination that holds a symlink. `symlink`/`readlink` and `cp -r` are excluded from the fuzzer's operation set for now, with the reason recorded in its header, so these three do not fail every seed and hide regressions in the fifteen operations that *are* in lockstep. ## 3.3.15

- **Fixed: the sync API now works in `opfs` mode on Firefox.** 3.3.14 recorded it as hanging there; the cause turned out to be one call. `OPFSEngine.read` fetched contents through `getFile()` + `arrayBuffer()`, and that Blob path needs main-thread involvement — so when the caller *was* a page main thread spinning on the SharedArrayBuffer, the continuation never ran and the read never returned. `write` had always used `createSyncAccessHandle`, which is worker-local, which is exactly why writes worked there and reads did not. `read` now uses the same primitive: Firefox passes, and the file is no longer materialised twice (Blob, then ArrayBuffer).

## 3.3.13

- **Removed an O(n²) term from block allocation — with an honest note on what that is worth today.** `allocateBlocks` scanned the free bitmap from block 0 on every allocation, one bit at a time, so each new file first walked past every block already in use: O(allocated) per create. It now uses next-fit (resume where the last allocation ended, wrap once) and skips fully-allocated bytes eight blocks at a time. Wrapping preserves the old guarantee that the volume only grows when no contiguous run exists anywhere.

  Against an in-memory handle this is a large win — per-create cost went from 8 µs rising to 16 µs by 16k files, to a flat ~7 µs (2.4× at that point, widening beyond). **Against real OPFS in Chromium it is not measurable.** Creating 15k files, before and after, in both modes:

  | mode | before (ms/op, batches of 1500) | after |
  |---|---|---|
  | `vfs` | 0.789 → 0.788 (flat) | 0.778 → 0.784 (flat) |
  | `hybrid` | 1.361 → 1.451 | 1.338 → 1.440 |

  The scan the change removes is ~8 µs at 16k blocks; a create against real storage costs ~800 µs, so it was always ~1% of the work and the old version was already flat in practice. The in-memory figure looked dramatic only because there the scan was half the total. Kept regardless: it is strictly better, costs nothing, and the removed term grows without bound — at 150k+ files the scan reaches the tens of microseconds where it would start to show. Measured by [create-scaling.spec.ts](tests/benchmark/create-scaling.spec.ts), which is checked in so the claim can be re-tested.
- Allocation is the last place to take a performance change on trust, so [block-allocator.test.ts](src/tests/block-allocator.test.ts) asserts the invariants rather than the speed: allocations never overlap (files keep their own bytes across creates, deletes and rewrites), freed space is reused rather than leaked, a large file fits into space freed by many small ones (which requires the wrap), block accounting stays exact, and a 4-seed fuzz runs 600 random create/delete/rewrite ops and verifies every surviving file byte-for-byte.
- **`statfs` reported invented numbers.** `statfsSync` returned fixed constants — always ~4 GB capacity with ~2 GB free, 10000 inodes with 5000 free — regardless of what the volume held, and never asked the engine; there was no STATFS opcode at all. Code checking free space before a large write got an answer unrelated to reality and would never see a full disk coming. It now reads the superblock the allocator maintains, via a new (additive) `OP.STATFS`. Free inodes are counted as distinct entries in the path index rather than by scanning the on-disk inode table, which would cost one read per slot.
- `statfs.test.ts` was itself self-referential — it built an `expectedStatFs()` locally and asserted the product matched those same fabricated constants. It escaped the 3.3.10 audit because it imports one product constant, so it did not look self-referential by that heuristic. Rewritten to assert `statfs` *tracks* the volume: free blocks fall by exactly the blocks a write consumes and return on delete, free inodes follow entry count, and the numbers are not identical regardless of contents.
- **Swept the sync and promise overloads too** ([overload-audit-sync.test.ts](src/tests/overload-audit-sync.test.ts), 18 differential cases). After 3.3.12 found three broken *callback* forms, the same optional-middle arguments needed checking on the other two APIs. **All clean** — but they are covered now, and against real `node:fs` rather than by inspection. This also unlocked something bigger: `_sync`/`_async` are instance fields, so `Object.create(VFSFileSystem.prototype)` plus a harness transport runs the **whole instance API in Node** — `cpSync` and friends were previously reachable only from a browser spec.
- **Found: hard links are copies.** `link()` duplicates the file rather than adding a second name for one inode, so writing through one name leaves the other unchanged — while both report `nlink: 2`. The earlier parity test passed because it only compared content immediately after linking. Not fixed: the on-disk format stores exactly one path per inode (`INODE.PATH_OFFSET`/`PATH_LENGTH`), so real links need a directory-entry table and a format migration, which is not something to do underneath existing volumes as a side effect. Documented under "Known divergences" in the readme, and the statfs test now pins the actual behaviour with a note that it should fail if links ever become real.
- 1247 Node tests pass, plus 27 browser tests across Chromium, Firefox and WebKit.

- **Fixed silent data loss in `truncate`/`ftruncate` on the server-worker path.** The method layer writes the length as a **float64** so files past the 4 GiB uint32 ceiling can be truncated; `server.worker.ts` (removed in 4.0.0) read it back as a **uint32**. ## 3.3.5

- **An unrecognised encoding is now an error, not silent UTF-8.** [encoding.ts](src/src/encoding.ts) `switch`ed on the raw encoding string with a `default:` that fell through to UTF-8, so `writeFileSync(p, data, 'utf9')` wrote the file and reported success. Node throws `ERR_INVALID_ARG_VALUE` ("The argument 'encoding' is invalid encoding. Received 'utf9'") and so do we — message asserted verbatim against real `node:fs`. A typo now surfaces at the call instead of as corrupted bytes discovered much later.
- **Encoding names are matched case-insensitively, as Node matches them — this was silently corrupting data.** Because the old `switch` compared exact lowercase literals, every non-lowercase spelling missed its case and hit the UTF-8 default. `writeFileSync(p, '4142', 'HEX')` wrote the four literal characters `"4142"` instead of the two bytes `41 42`; `'Latin1'` and `'BASE64'` were mangled the same way. All of Node's aliases now normalise properly (`utf8`/`utf-8`, `utf16le`/`utf-16le`/`ucs2`/`ucs-2`, `latin1`/`binary`, `base64`, `base64url`, `ascii`, `hex`).
- **`base64url` is supported.** It had no case at all, so it fell through to UTF-8 — a base64url write produced the literal text. Added to the `Encoding` type, encoded without padding and with the url-safe alphabet.
- **The base64 parser reproduces Node's leniency instead of `atob`'s strictness.** `atob` throws on unpadded input and on `-`/`_`, so `writeFileSync(p, 'aGVsbG8', 'base64')` — valid in Node, decoding to "hello" — **threw**. The new decoder skips characters outside the alphabet (`'aGVs!bG8'` → "hello"), treats `=` as a terminator (`'aGVs=bG8'` → "hel"), tolerates missing padding, drops a trailing group of one character, and accepts the url-safe alphabet under the plain `base64` name — each behaviour captured from `Buffer.from(…, 'base64')`.
- **The hex parser no longer injects zero bytes.** It used `parseInt` per pair, which turns an invalid pair into `NaN` and then a silent `0x00` in the middle of the output: `'41zz42'` produced `[0x41, 0x00, 0x42]` where Node produces `[0x41]`. It now stops at the first pair that is not two hex digits, and ignores a trailing odd character.
- **Fixed the `ascii` encode direction.** Node masks to 7 bits when *decoding* ascii but not when *encoding* it — `Buffer.from('é', 'ascii')` is `[0xE9]`, identical to latin1. We masked on the way in too, so every character above 0x7F was mangled on write. `utf16le` now also drops a trailing odd byte rather than emitting a replacement character, matching Node.
- **`readdir` and `readlink` honour their `encoding` at last.** Both recognised only `'buffer'` and returned UTF-8 strings for everything else, ignoring `latin1`/`hex`/etc. and accepting invalid names without complaint. Both now validate and decode properly.
- **Performance: the decode path got faster, not slower.** `decodeBuffer`/`encodeString` constructed a `new TextDecoder`/`TextEncoder` on *every call*; those are now module singletons, and the validation fast-path recognises `'utf8'`/`'utf-8'` with two comparisons before any lowercasing. Net effect on a 2 KB UTF-8 decode: **141 ns/op → 108 ns/op**. Large `latin1`/`ascii` decodes also switch from per-character string concatenation to chunked `fromCharCode.apply`, which additionally fixes a stack overflow on buffers past a few hundred KB.
- Adds [encoding-parity.test.ts](src/tests/encoding-parity.test.ts) (49 cases, every expectation captured from real `node:fs`/`Buffer`). One case in [encoding.test.ts](src/tests/encoding.test.ts) asserted the incorrect `ascii` encode masking and was corrected. 882 tests pass.

## 3.3.4

- **`appendFile` honours its `options` argument, which it had been discarding entirely.** `encoding`, `mode`, `flag`, `flush` and `signal` were all dropped on the floor: the implementation encoded every string as UTF-8 and issued a bare APPEND regardless of what was asked. Two of those were silent data bugs — `appendFileSync(p, 'é', 'latin1')` wrote the two UTF-8 bytes `C3 A9` instead of the one byte `E9` Node writes, and `{ flag: 'w' }` **appended when it was asked to truncate**, so a caller using `appendFile` as a general write with an explicit flag got a file that grew without bound. Now: string data is encoded with the requested encoding (bare-string shorthand included), binary data passes through untouched, `flag` selects the open mode, `mode` applies at creation with the umask subtracted and is ignored for an existing file, `flush` fsyncs, and an aborted `signal` throws before any request is issued. All verified against real `node:fs`.
- **The fast path is preserved.** A default `appendFile(p, data)` still issues the single APPEND op it always did, byte for byte. Only a request that APPEND cannot express — a creation mode, a non-`'a'` flag, or a flush (`engine.append` takes no flags) — takes the open → write → close route, where the flag and mode land on the open itself. `O_APPEND` makes the engine write at end-of-file regardless of position, so appends stay correct on that path too.

## 3.3.3

- **`open` now honours its `mode`, completing the file-creation half of 3.3.2's mkdir fix.** The OPEN opcode carried no mode payload, so `openSync(p, 'w', 0o600)` created the file with the hardcoded `DEFAULT_FILE_MODE` and a caller asking for a private file silently got a world-readable one. The mode now travels as a 4-byte LE payload and [engine.ts](src/src/vfs/engine.ts) subtracts the umask via a new `fileModeFor`, mirroring `dirModeFor`. Two `open(2)` details are reproduced deliberately, both verified against real `node:fs`: the umask applies (mode 0o777 yields 0o755), and **the mode is consulted only when the file is actually created** — re-opening an existing file with a different mode leaves its permissions alone. The default is bit-identical to before: an omitted mode means Node's 0o666, which under the default 0o022 umask is the historical 0o644. Wire format stays additive, so a client that sends no payload keeps the old behaviour, and the zero-allocation `encodeRequestU32` means the mode costs OPEN nothing measurable.
- **`writeFile`'s `mode` option was applied by chmod-ing after the write, which was wrong twice over.** chmod does not subtract the umask (so `{ mode: 0o777 }` produced 0o777 where Node gives 0o755), and it fired unconditionally — re-permissioning a file that already existed, which Node explicitly does not do. Now that OPEN carries a mode, a `writeFile` with an explicit mode routes through open → write → close so the mode rides along with the creation, exactly as in Node. **The hot path is untouched:** a `writeFile` with no mode still takes the single-op WRITE fast path, byte for byte as before, so the extra round-trips only occur in the rare case that actually asks for a mode. The fd path also honours `flush` now, in both the sync and async variants, which it previously ignored.
- Adds 8 cases to [mode-parsing.test.ts](src/tests/mode-parsing.test.ts) (engine-level create-with-mode, umask subtraction, the default, and the mode-ignored-on-existing-file rule; plus the method-layer encoding and the fresh-payload-per-call guarantee for async open). The two `writefile-mode` tests that asserted the old chmod-after-write behaviour were rewritten to assert the Node behaviour they should have been asserting. 817 tests pass.
- Known gap, unchanged: `appendFile` ignores its `options` argument entirely — both `mode` and `encoding` — so an append always creates with the default mode and encodes as UTF-8. Documented in the readme; worth its own fix.

## 3.3.2

- **`mkdir` now honours the `mode` you give it, and `mkdtemp` creates a private 0700 directory — fixes software that creates a restricted directory and stats it back.** `mkdir`'s mode was silently discarded end to end: the method layer encoded only the `recursive` flag, and the engine created every directory with a hardcoded `DEFAULT_DIR_MODE`, so `mkdirSync(p, { mode: 0o700 })` produced 0755. Programs that make a *private* directory treat the widened mode as a security failure rather than a cosmetic one — Chrome's `ProcessSingleton` `mkdtemp()`s its socket directory and `CHECK`-fails with *"Temp directory mode is not 700: 755"*, killing the browser at startup. The mode now travels as a 4-byte LE payload (the shape `chmod` already used) and [engine.ts](src/src/vfs/engine.ts) subtracts the umask exactly as `mkdir(2)` does in the kernel, at every level a recursive `mkdir` creates — matching Node, which passes the mode to each level. `mkdtemp` creates with `S_IRWXU` per `mkdtemp(3)`. **The default path is bit-identical:** an omitted mode means Node's `0o777`, which under the default `0o022` umask is the historical 0o755. The one visible delta is a *configured* permissive umask — `umask: 0o002` now yields 0775 where the old hardcoded mode capped it at 0755, which is what Node and `mkdir(2)` do. The wire format is additive, so a client that sends no payload still gets the old behaviour.
- **Node-exact mode parsing across `mkdir`, `chmod`, `fchmod`, `lchmod` and `writeFile`.** Modes were coerced numerically, so an octal *string* — which Node accepts, and which `{ mode: '0700' }` makes natural to write — became decimal 700 (= 0o1274): a mode nobody asked for, applied silently. New [mode.ts](src/src/methods/mode.ts) reproduces Node's `parseFileMode`, including the bare-string shorthand `mkdirSync(p, '0700')`. Invalid modes now throw Node's own errors instead of writing garbage: `ERR_INVALID_ARG_VALUE` for a non-octal string, `ERR_INVALID_ARG_TYPE` for a non-number (an omitted `chmod` mode used to coerce to NaN → chmod 000), `ERR_OUT_OF_RANGE` for negative/fractional/over-u32. Messages and `code` values were captured from real `node:fs` and are asserted verbatim, down to Node's "property" vs "argument" wording for dotted names. `Mode = number | string` is exported and the public signatures widened.
- **Performance: the mode plumbing costs ~5 ns/op instead of ~204 ns.** The obvious encoding — a throwaway `Uint8Array` + `DataView` per request — cost more than the four stores it performed, on a path taken by every `mkdir` and `chmod`. New `encodeRequestU32` ([opcodes.ts](src/src/protocol/opcodes.ts)) writes the value straight into the request buffer, allocating nothing extra; it is byte-for-byte identical to the payload form (asserted). The async path still allocates a per-call buffer deliberately: `postMessage` happens after an `await`, so a shared scratch buffer would let concurrent calls clone each other's mode. No other request path changed.
- **Fix: three internal `engine.mkdir` calls passed a mode into the `flags` parameter** ([repair.worker.ts](src/src/workers/repair.worker.ts), [sync-relay.worker.ts](src/src/workers/sync-relay.worker.ts)) — `0o040755 & 1` happens to be 1, so they had always been running as recursive mkdirs by accident. Rewritten as `mkdir(path, 1, 0o755)`, which is exactly what they were already doing; behaviour is unchanged, the intent is now stated.
- Adds [mode-parsing.test.ts](src/tests/mode-parsing.test.ts) (33 cases: parser parity with captured Node output, wire encoding, the no-shared-buffer guarantee, `encodeRequestU32` byte-equivalence and round-trip). Documented in the readme under [File Permissions](readme.md). 809 tests pass.
- Known gaps, unchanged here and now documented: `open(path, flags, mode)` still drops its mode (files are created with the default — `writeFile`'s `mode` option works, via a chmod after the write), and `opfs` fallback mode stores no permission metadata, so directories there always read back as the synthetic 0755.

## 3.2.13

- **New fairness (bakery) ticket lock over the control SAB, so a host can safely share ONE control SAB across multiple sync clients.** The sync FS protocol stages each request into a single request/response slot serviced by one relay worker against one OPFS handle. A host that deliberately points several sync clients at one SAB (e.g. a dev container running multiple exec Web Workers + the main thread, all driving a single relay so only one OPFS handle is ever open) needs those clients to take turns — otherwise two stage a frame into the slot at once and the relay reads a torn request. `syncRequest` now wraps each op in `acquireFsLock`/`releaseFsLock` ([fs-lock.ts](src/src/protocol/fs-lock.ts)), a ticket lock: each client draws a ticket via `Atomics.add` and is served in strict arrival order. This is **fair** (no starvation), unlike a plain CAS spinlock where a waiter can lose indefinitely and a host's "self-heal" timeout then force-steals the lock from a *live* holder — re-introducing the exact double-holder corruption the lock prevents. The two ticket counters reuse header bytes 4/8 (the legacy `OPCODE`/`STATUS` slots in [opcodes.ts](src/src/protocol/opcodes.ts), kept as aliases) which the protocol never reads or writes — op code and status travel in the payload, and `syncRequest`/the relay only ever touch header indices 0/3/6. **No cost to the default single-client case:** uncontended, `NEXT` and `SERVING` march in lockstep so every acquire is satisfied immediately via a fast-path `Atomics.load` (a couple of atomics, never `Atomics.wait` — which is illegal on the browser main thread anyway). Dead/wedged-holder recovery is conservative: a waiter only advances past a stuck ticket after `HOLDER_STUCK_MS` (30 s, matching the relay-heartbeat stall ceiling the library already tolerates for a WebKit OPFS truncate), far longer than any single live op, so a healthy holder is never stolen from. The lock captures `this.ctrl` once per op so a leader handoff that swaps the SAB mid-op can't release a different SAB than it acquired. `acquireFsLock`, `releaseFsLock`, `SAB_OFFSETS`, and `SIGNAL` are now exported ([index.ts](src/src/index.ts)) so a host sharing a SAB across *raw* sync clients can serialize them with the same lock the library uses internally. Adds [fs-lock.test.ts](src/tests/fs-lock.test.ts) (uncontended never blocks, strictly sequential tickets, NEXT/SERVING lockstep). 736 tests pass.

## 3.2.12

- **Reserve the free-block bitmap region for the maximum block count, not the initial one — fixes silent data corruption on any VFS that grows past ~62 MB.** The on-disk bitmap region was sized at format time for `INITIAL_DATA_BLOCKS` (1024 → ~1984 bytes after alignment = capacity ~15,872 blocks ≈ 62 MB), but `allocateBlocks`/`maybePreGrow` grow `totalBlocks` and the in-memory bitmap **without enlarging that region**. Once the filesystem exceeded ~62 MB the bitmap spilled past `dataOffset` and overlapped the first data block(s): the bitmap write and the file's bytes clobbered each other, and on the next mount the bitmap read back partly as file data → garbage allocation bits. Continued operation then drove `FREE_BLOCKS` to a u32 underflow (observed as `Corrupt VFS: free blocks (4294942324) exceeds total (594400) — Falling back to OPFS mode`). This was **not** an alloc/free counter desync (the in-memory `FREE_BLOCKS === bitmap-clear-bits` invariant holds for every mutation — verified by a 5-seed fuzz) and **not** a shutdown artifact (reproduces with a clean, fully-flushed remount). The fix ([layout.ts](src/src/vfs/layout.ts) `calculateLayout` now reserves `ceil(MAX_DATA_BLOCKS / 8)` ≈ 500 KB so the bitmap can represent up to ~16 GB and never reaches the data region): `format` reserves for the engine's `maxBlocks`, `growAndAllocate`/`maybePreGrow` are capped at the reserved capacity (throw ENOSPC rather than overflow), and `mount` rejects an already-overflowed legacy file instead of trusting a garbage bitmap. The async server-worker dispatch now also catches engine throws and returns EIO (the sync relay already did) so an ENOSPC can't hang an awaiting client. Adds [bitmap-region-overflow.test.ts](src/tests/bitmap-region-overflow.test.ts) (grows past the old cap + fuzz; asserts the count matches the bitmap in memory and across a remount, with byte-identical file readback). 730 tests pass.

## 3.2.11

- **`growInodeTable` now shifts the post-table region in chunks instead of buffering it whole — fixes "Array buffer allocation failed" when growing the inode table on a large VFS.** When the inode table fills and doubles, everything after it (path table + bitmap + **all file data**) must shift right by the growth amount. The old code did this with a single `new Uint8Array(afterSize)` spanning the entire data region — hundreds of MB for a large bundle (e.g. the Telegram AppDir) — which throws on the transient allocation and aborts the write, corrupting/truncating the store. The shift now streams in 8 MB chunks scanned **end→start**: because every chunk's destination lands `growth` bytes higher than its source and the highest-offset chunk moves first, a write can never clobber bytes an as-yet-unread (lower-offset) chunk still needs, so the overlapping move stays correct. The new-inode zero-fill is chunked the same way (`growth` doubles each grow and can itself exceed a comfortable single allocation). Adds [inode-growth-integrity.test.ts](src/tests/inode-growth-integrity.test.ts) (forces many table doublings with mixed file sizes, asserts every file reads back byte-identically) and [repro-largefile.test.ts](src/tests/repro-largefile.test.ts) (large single-file round-trips, including the observed 542,880-byte ELF). 727 tests pass.

## 3.2.10

- **Gate idle/init pre-growth (`maybePreGrow`) behind the WebKit check — fixes a major Chromium/Android sync-FS regression introduced in 3.1.0.** The 64 MB free-tail headroom (`maybePreGrow`, added 3.1.0) exists for **one reason**: on WebKit a size-changing OPFS call (`truncate` / extending `write`) blocks until the page main thread returns to its event loop, so a spinning sync caller deadlocks any in-request growth — growth must therefore be done proactively at idle. On Chromium/Gecko there is **no such deadlock**; in-request growth via `allocateBlocks` is safe (and is exactly what pre-3.1.0 did). There the proactive growth was pure overhead: a forced OPFS `truncate` + flush run from the dispatch loop after every 25 ms-quiet gap, plus a one-time 64 MB `truncate` at init — cheap on desktop SSD but **slow on mobile flash, stalling the relay loop between ops** (read *and* write latency, since a busy relay can't service the next request). It is the same class of WebKit-only workaround that 3.2.8 gated behind `IS_WEBKIT`; pre-growth was simply missed. Both call sites (`preGrowIfQuiet` in the dispatch loop, and the init pre-grow) now run only when `spinningNeeded()` is true (WebKit, or forced via `forceSpin` / `self.__fs_force_spin`). WebKit behavior is unchanged; Chromium/Firefox/Android fall back to on-demand growth — measured **superfast again on Android Chrome, matching 3.0.55**. The engine's `maybePreGrow` method is untouched (unit tests unchanged); only the worker's *calls* to it are gated. 718 tests pass.

## 3.2.8

- **Gate the three WebKit-only dispatch-loop workarounds behind an engine check so they no longer run on Chromium/Firefox.** The sync-relay leader loop carries three mechanisms that exist solely to defeat WebKit's lost cross-thread `Atomics.notify` + main-thread-brokered MessagePort delivery (a sync caller busy-spinning the page main thread starves both): (1) the post-response **busy-poll spin** (0.25ms `performance.now()` spin to catch the next request without a park), (2) the `yieldToEventLoop` **1ms starvation-timer race** against the self-ping, and (3) `awaitResponseConsumed`'s **5ms-sliced** lost-wake-proof wait. - **The inbound external-change path now runs the same bookkeeping as the outbound path.** `handleExternalChange` (applied when the `FileSystemObserver` detects an external OPFS change) updated the engine directly but skipped all the symlink-alias and pending-sync maintenance `notifyOPFSSync` does, so external mutations silently bypassed it. Now an external write to a symlink's target re-mirrors the dependent links; an external rename reroutes pending child syncs and re-keys aliases; an external delete drops aliases and re-mirrors now-dangling links; and an external write onto a path that is a directory in the VFS converges (removes the dir, writes the file) instead of being dropped with `EISDIR`
- **Echo suppression is now content-based, so a genuine external write within the 3 s grace window is no longer mistaken for our own echo.** The mirror worker records a content hash of every byte range it writes; an observed `modified`/`appeared` is suppressed only when the bytes match what we wrote (within the window) rather than on timestamp alone. A freshly-created file can fire `appeared` with a stale empty snapshot that wouldn't match our hash — so when the observed bytes differ but we recently wrote the path, the worker re-reads the current bytes once before treating it as external, preventing a 0-byte bounce that would clobber the file. (`disappeared`/`moved`, which carry no content, keep the time-based check.)
- **`rename()` now rejects POSIX type conflicts.** The engine would overwrite a directory with a file (or vice versa), diverging from Node and producing a mirror that can't represent the result (a `write` can't turn an OPFS directory into a file). `rename` now returns `EISDIR` for file→existing-directory and `ENOTDIR` for directory→existing-file. Replacing a non-empty *directory* with another directory stays allowed — Vite's `.vite/deps_temp_<hash>` → `.vite/deps` commit relies on it, and the mirror handles it via `renameDirInOPFS`
- Tests: unit tests for the rename type guards (file→dir / dir→file rejected; file→file and dir→dir replace still allowed); the `opfs-mirror-external` E2E spec now asserts a within-grace external write reaches the VFS (#2) and that an external target change re-mirrors its dependent link (inbound symlink) — both verified to fail before these fixes

## 3.2.5

Fixes from a multi-agent adversarial audit of the OPFS-mirroring system. Five confirmed mirror-vs-VFS divergences, all affecting normal (single-tab, local) usage:

- **Write-coalescing could reorder a write ahead of an intervening delete, losing the file.** The mirror worker coalesces queued `write` events for the same path, but the scan skipped past a `delete`/`rename` sitting between two writes and merged the new payload onto the *earlier* write — turning queue `[write, delete, write]` into `[write, delete]` and dropping the re-created file from OPFS. Coalescing now stops at the first intervening op for that path (`coalesceWriteIndex`, unit-tested) and appends in order instead. Needed queue backpressure (large/slow writes) to trigger
- **A mirror op that threw was dropped and never retried.** `processNext` treated success and failure identically — on any throw it logged and marked the event completed, permanently diverging the OPFS file from the VFS. Transient WebKit failures (`NoModificationAllowedError`/`NotFound` under sync-access-handle contention, which Chromium never throws) hit exactly this. Write/delete/mkdir now retry with backoff before giving up, matching the hardening the rename path already had
- **`open()` that creates or truncates a file was never mirrored.** `OP.OPEN` set no sync metadata, so `open(p,'w')`+close (a touch), and `open(existing,'w')`+close (which truncates inside `engine.open`, bypassing `OP.TRUNCATE`), left the mirror missing the file or holding stale pre-truncate bytes. `OP.OPEN` now mirrors on `O_TRUNC` or a creating `O_CREAT` (a cheap `exists()` pre-check avoids re-mirroring an `O_CREAT` open of an already-present file)
- **Removing or renaming-away a symlink's target left dependent links stale.** The 3.2.3/3.2.4 alias re-sync only fired when a target was *written*; `unlink`/`rmdir`/`rename` of a target never re-mirrored the links pointing at it, so they kept the deleted content instead of becoming the empty dangling-placeholder. The UNLINK/RMDIR/RENAME branches now `resyncSymlinksUnder` the removed path (covering a single file or a whole removed/renamed subtree)
- **Chained symlinks didn't cascade.** Writing the final target of `L1 → L2 → file` re-mirrored only `L2`; `L1`'s snapshot stayed stale. `flushPathSync` now cascades the re-sync to links pointing at the just-flushed path (success branch only, so a symlink cycle — which reads non-zero — can't loop)
- Tests: unit tests for `coalesceWriteIndex` (incl. the reorder-across-delete case); E2E `opfs-mirror-open` spec and new cases in `opfs-mirror-symlink` (target deletion → placeholder, chained-link cascade) — all verified to fail before these fixes

Audit findings deferred as out-of-scope or design-level (not fixed here): the inbound `handleExternalChange` path bypasses symlink-alias and pending-reroute bookkeeping (only matters with external `FileSystemObserver` changes); the 3 s echo-grace window can suppress a genuine external write that lands within 3 s of our own write to the same path (fundamental to timestamp-only echo suppression — needs content/version tagging); and `rename(file → existing-dir)` mirrors as a write that can't replace an OPFS directory (stems from the engine permitting a non-POSIX file-over-directory rename).

## 3.2.4

- Tighten the symlink→target alias tracking added in 3.2.3 so it no longer leaks entries. The map was forward-only (target → links), so a link removed by `unlink`, moved by `rename`, or replaced by a re-created symlink left a stale entry that accumulated over a long session. Added a reverse map (link → target) and routed all mutations through `registerLink`/`deregisterLink`, which keep both maps consistent and prune a target's set once it empties. A single `unlink` deregisters in O(1); a recursive `rmdir` or a directory `rename` deregisters every link under the prefix (`collectKeysUnder`), and a `rename` re-registers the moved links at their new paths so they keep tracking their target. Stale entries no longer accumulate
- Tests: unit tests for `registerLink`/`deregisterLink` (no-leak/prune-on-empty/move-on-recreate) and `collectKeysUnder` (exact + strict-descendant matching); the `opfs-mirror-symlink` E2E spec gained a case that renames a symlink and confirms it still re-syncs when its target is later rewritten

## 3.2.3

Two more OPFS-mirror divergence bugs found while auditing the mirroring path (separate from the 3.2.1/3.2.2 rename family). Neither touches the read/write hot path — the changes are confined to the symlink and external-change branches.

- **Local write after an external change was silently dropped from the mirror.** When the `FileSystemObserver` reported an external OPFS change, the relay added the path to `suppressPaths` and applied the change to the engine *directly* (no mirror echo). Nothing consumed that suppression until the next genuine local write to the same path, which `notifyOPFSSync` then skipped — so a `writeFileSync` following an external edit updated the VFS but never reached OPFS, diverging permanently. The mirror worker's own `isOurEcho` (pending/completed tracking) is the authoritative echo guard, so the redundant, buggy relay-side `suppressPaths` layer is removed entirely. Only affected setups using external-change sync
- **Symlinks mirrored as files went stale and dangling links were dropped.** OPFS has no symlinks, so a symlink is mirrored as a regular file holding its target's content (a snapshot). (1) A dangling symlink (target missing) read `ENOENT` and was silently never mirrored. (2) The snapshot went stale when the target was later rewritten, because a write notifies the *target's* path, not the link's. The relay now tracks symlink→target aliases (`resolveLinkTarget`, keyed by resolved absolute target, resolving relative targets against the link's directory): a target write re-mirrors its links, and a dangling link is mirrored as an empty placeholder that fills in once the target appears. Alias lookup is a single `Map.get` per write that only iterates when the written path is actually a symlink target
- Tests: `resolveLinkTarget` unit tests (relative/absolute/`..` resolution); end-to-end Playwright specs against the dist build with the real OPFS mirror — `opfs-mirror-external` (local write survives an external change; self-skips where `FileSystemObserver` is unavailable) and `opfs-mirror-symlink` (link tracks target updates, relative-target resolution, dangling placeholder + heal). Both verified to fail before these fixes
- Added `tests/benchmark/opfs-mirror-rename.spec.ts` (3.2.2's directory-rename fix) as a real-browser end-to-end regression alongside the existing unit coverage

## 3.2.2

- Fix recently-written files being lost from the OPFS mirror when their parent **directory is renamed** — the same class of bug as 3.2.1, found while auditing for more. `engine.rename` of a directory moves the entire subtree to the new path in a single op, but pending debounced child syncs (`pendingPathSyncs`) are keyed by absolute path: after the rename a child's old key no longer resolves, so when its 50 ms flush fires `engine.read` returns `ENOENT` and the child is silently dropped. The directory itself is mirrored via `renameDirInOPFS`, which only moves files **already** in the OPFS mirror — so a child written inside the debounce window (never flushed) was lost entirely. This hits the exact Vite `.vite/deps_temp_<hash>` → `.vite/deps` commit the rename path targets: the most-recently-written deps chunks could vanish from the mirror
- The RENAME handler now re-keys every pending child sync from the old directory prefix to the new one (`planPendingReroutes`) before emitting the rename op, so each child flushes against its real post-rename location and lands in the mirror after the directory rename. Strict-descendant matching only (`oldDir + '/'`), so file renames and sibling paths sharing a name prefix (`/d` vs `/d2`) are unaffected
- Confirmed the analogous paths are already safe and need no change: recursive `cp`/`cp -r` recurses in JS and emits a per-leaf op (file → `copyFileSync`, dir → `mkdirSync`, symlink → `symlinkSync`), so every file is mirrored individually; and `rm -rf` / `rmdir` strand no content because a stale child flush reads `ENOENT` and correctly no-ops (the desired end state is "deleted"). Only directory **rename** preserves the subtree under a new path, which is why it alone needed rerouting
- Add `planPendingReroutes` unit tests (Vite deps case, strict-descendant matching, file-rename no-op) alongside the existing `planRenameMirror` coverage

## 3.2.1

- Fix atomic-write renames (`write temp → rename(temp, final)`) silently dropping from the OPFS mirror. The relay's `notifyOPFSSync` debounces write bursts (`SYNC_DEBOUNCE_MS`) before reading the file and mirroring it; but a temp file in the atomic-write pattern is created *and* renamed within that window, so its pending sync was cancelled and it was **never** mirrored. Forwarding a plain `rename` op to the sync worker then failed with "source not found" because the source never existed in OPFS — the destination diverged from the VFS. (This is the root cause the 3.0.54/3.0.55 mirror-side retries were papering over for the file-rename case.)
- A regular-file rename is now mirrored deterministically as `write(newPath)` + `delete(path)` using the destination's authoritative bytes read straight from the engine at `newPath` (the rename already succeeded in the VFS), instead of a copy-the-source `rename` op — so it no longer depends on whether the temp source was ever mirrored. The pending debounced syncs for **both** the old and new paths are cancelled first. Directory renames (`engine.read` returns `EISDIR`) still fall back to a real `rename` op, which the sync worker handles via `renameDirInOPFS` — the source directory *was* mirrored, unlike a write-temp
- Add `tests/opfs-sync-rename.test.ts` covering the `notifyOPFSSync` RENAME branch: an atomic-write rename whose temp source was never mirrored emits `write(final)` + `delete(temp)` (not a `rename` op); a directory rename (engine reports `EISDIR`) falls back to a `rename` op; and pending debounced syncs on both the old and new paths are cancelled

## 3.2.0

- Multi-tab synchronous FS now works on Safari for **follower** tabs, by running the VFS instance inside a worker. A follower's sync op busy-waits the calling thread; on the main thread that is a spin-loop, and WebKit gates a worker's MessagePort delivery on the parent page's main thread — so the leader's reply can never arrive and the op deadlocks. Run the instance in a worker and the wait becomes a real `Atomics.wait`, the main thread stays free to pump delivery, and follower sync works (the same fast SAB transfer, worker→worker). ## 3.0.53

- Add leader-transition readiness tracking so callers can tell when sync FS ops are actually safe across a leader handoff. ## 3.0.52

- Replace the main-thread spin-wait's fixed wall-clock timeout (10 s, briefly bumped to 60 s) with a worker-liveness heartbeat. `Atomics.wait` is disallowed on the browser main thread, so sync FS calls spin on `Atomics.load`; the old code aborted the call — and the in-flight FS operation — after a fixed elapsed time, which is wrong both directions. A genuinely slow op gets killed mid-flight (a single `rename`/`copy` over a freshly-installed `node_modules` is thousands of OPFS handle awaits and can legitimately take tens of seconds — 10 s was being hit during `create-strapi-app`'s git init), while a truly wedged worker still blocks for the full timeout. The relay worker now bumps a counter in the control SAB (`SAB_OFFSETS.HEARTBEAT`, the previously-reserved Int32 slot) on a 1 s `setInterval` started before init begins; because that timer keeps firing while the worker is parked on an `await` inside a long op, the main thread can tell "slow" from "dead". The spin-wait aborts only if the heartbeat stalls for `SPIN_STALL_TIMEOUT_MS` (20 s) — there is no upper bound on a *progressing* op
- Fix a latent corruption/hang in `syncRequest`'s multi-chunk send path — a single sync write whose encoded request exceeds the SAB data window (`sabSize - HEADER_SIZE` ≈ 2 MB by default), i.e. `writeFileSync`/`writeSync`/`appendFileSync` of more than ~2 MB. The final request chunk is sent with `SIGNAL.CHUNK` and the worker never acks it (only non-final chunks get a `CHUNK_ACK`), so after the send `ctrl[0] === CHUNK` — but the response-wait waited on `SIGNAL.REQUEST`, so the spin-wait fell through immediately and read the still-stale request bytes as the response, then wedged spamming `CHUNK_ACK`s. It now waits on the frame it actually wrote last (`CHUNK` for multi-chunk requests, `REQUEST` otherwise), mirroring the async-relay's send path. Combined with the heartbeat change above, this would otherwise have been an unkillable hang

## 3.0.51

- Fix O(N²) regression introduced in 3.0.49. The implicit-directory guard added in 3.0.49 (`isImplicitDirectory(path)` checks in `write`, `symlink`, `link`, `copy`, plus `mkdir`, `stat`, `lstat`, `access`, `realpath`, `exists`) called `rebuildImplicitDirs` on every invocation, which is O(N×depth) over total pathIndex entries. ## 3.0.48

- Eliminate residual race in the SW broker heartbeat: stop calling `close()` on the previous control port at all. If the disentangle landed before the SW processed `register-server`, any follower `transfer-port` already in the SW inbox was dispatched against a now-detached `serverPort` and silently dropped (postMessage to a disentangled peer is a no-op per spec)
